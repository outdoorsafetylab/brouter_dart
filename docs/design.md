# Design

Why the port looks the way it does. Comments in the code refer to these sections as `docs/design.md D4` and so on.

The goal: compute hiking routes offline on phones. BRouter's Java engine runs on Android but not on iOS, which has no JVM, so the routing engine is ported to pure Dart and both platforms run the same code. Data and profiles stay in BRouter's own formats: `rd5` segments, `lookups.dat` and `.brf` profiles.

## D1 Scope: the routing engine only

BRouter v1.7.10's routing engine is five modules, about 19,300 lines under `src/main`:

| Module | Lines | What | Ported |
|---|---|---|---|
| util | 3,000 | bit I/O, CRC, long sets, LRU | only what the other modules use |
| codec | 1,600 | bit decoding of the micro-caches inside an rd5 | yes |
| expressions | 1,900 | parsing and evaluating `lookups.dat` and `.brf` profiles | yes |
| mapaccess | 3,200 | reading rd5 segments, nodes and links, caching | yes |
| core | 9,600 | path search, cost model, tracks | yes, without voice hints and the GPX/KML/CSV/JSON writers (about 2,400 lines) |

The output is Dart objects: the points (coordinates, elevation), distance, ascent, cost and time. Callers convert to whatever file format they need.

Not ported: building rd5 files (the weekly segments from brouter.de are used as they are), the map creator, the server, the Android app, voice hints, nogo areas.

## D2 Pinned to v1.7.10

The port follows one released version. Moving to a newer one is a change of its own, with new reference data.

## D3 A pure Dart package, native platforms only

- No Flutter dependency: `dart test` runs every comparison on a desktop.
- Android, iOS and macOS. Not the web: the decoder needs 64-bit integer bit operations, and integers on the web have 53 bits, bit operations 32.
- Routing should run in the background, but the package starts no isolate of its own; the caller decides where it runs.

## D4 Java's types reproduced, trigonometric and exponential functions written in Dart

The Java engine evaluates profiles and cost factors in `float` and sums costs in `int`. Dart has only the 64-bit `double`, so wherever Java uses `float`, every step is rounded to Float32. Addition, subtraction, multiplication, division and square root computed in double and then rounded give exactly the float result, so this part reproduces bit for bit.

The trigonometric and exponential functions do not: the engine calls `Math.cos`, `Math.sin`, `Math.atan2` and `Math.exp` (`CheapRuler`, `CheapAngleMeter`, `StdPath`, `KinematicPath` and others). Java's `Math` does not promise the same result everywhere, and Dart calls each platform's math library, which may differ in the last bit between Android, iOS and macOS. Measured on cosines at Taiwan's latitudes, Java and Dart differed by 1 ULP on 2 of 40 values.

So:

- The Dart side implements these four functions in pure Dart after fdlibm's algorithms (`lib/src/util/fdlibm.dart`). They use only arithmetic and bit operations, so every platform gets the same result.
- The Java reference uses `StrictMath`, which is specified to follow fdlibm and so matches the Dart port bit for bit. `golden/` builds BRouter v1.7.10 from source after switching those four `Math` calls to `StrictMath` with `golden/strictmath.patch`, and changes nothing else.
- The cost: the reference can differ in the last bit from an unpatched BRouter on these four functions, which changes the chosen route only between two routes of almost equal cost.

Why: a slightly different cost can pick another route. Only bit-for-bit equality lets the Java engine serve as the reference; with a tolerance, every difference would need someone to decide whether it is rounding or a bug.

## D5 The Java engine is the reference

`golden/` holds a small Java program that uses the patched BRouter of D4 to write the comparison data, in layers (`golden/FORMAT.md`):

0. **Util**: the low-level functions, value by value.
1. **Decoding**: every node of the segments with its coordinates, elevation and links, and every link's tags.
2. **Profiles**: for given tag combinations, the cost factors and variables the `hiking-mountain` and `trekking` profiles compute.
3. **Routes**: for a set of start and end points, the point sequence, cost, distance, ascent and time.

Rules:

- Every layer must match exactly; there is no tolerance.
- The comparison data is regenerated by that program, never edited by hand.
- The inputs must be reproducible. brouter.de replaces its segments weekly under the same file names, and old files cannot be fetched again, so one copy of the inputs (two rd5 segments, `lookups.dat`, two profiles) is kept as the assets of a GitHub release named after the download date (`golden-input-2026-11-23`). `golden/data/INPUT` records the release and each file's SHA-256, and the tests download that release. The rd5 files stay out of git.
- These inputs are not refreshed weekly. Newer segments come as a new release with regenerated data; old releases stay.
- Route cases start and end only at public trailheads, summits, huts and landmarks, never at anyone's track or position. They cover short routes (under 1 km), day hikes (10–20 km), multi-day routes (over 30 km), routes across both segments, a start far from the network, and unreachable targets.

## D6 Three stages, each complete only when its layer matches

1. **Decoding**: codec and mapaccess, against layer 1.
2. **Profiles**: expressions, against layer 2.
3. **Path search**: core, against layer 3. Then the same comparison runs on an Android phone and an iPhone to confirm that phones give the same results as the desktop, and the routes are timed there.

The benchmark (`bin/bench.dart` on the host, `bench_app/` on phones, `golden/src/Golden.java bench` for Java) stays in the repository as a baseline; it is not run on a schedule. No performance tuning before every layer matches.

## D7 Decoding and profiles are compared separately

The modules depend on each other as util → codec → expressions → mapaccess → core. mapaccess's `NodesCache` passes the expressions' way profile into decoding as codec's `TagValueValidator`, which decides which links to keep; decoding needs only that interface. So both sides of the layer 1 comparison decode with the same keep-everything validator, and decoding and profiles can be checked independently. Their behaviour together is covered by the routes of layer 3.

## Verification

- Every change: `dart analyze` clean, `dart test` green, every layer matching.
- The comparison itself: each layer was checked with at least one mutation (a bit read off by one, Float32 rounding removed, a cost plus one) to confirm it turns red.
